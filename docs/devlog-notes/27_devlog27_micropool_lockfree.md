# Devlog #27 - Rayon is NOT for games - use this instead

- 视频: https://youtu.be/QFQkqFSg8Z4 （12:54，2025）
- 类别: 物理 | ⭐⭐ 多线程调度：游戏为何不该用 Rayon

## 一句话
Rayon 为吞吐量而非延迟设计：主线程派发后干等、工作线程可能顺手做 50ms 的世界生成导致卡顿尖峰；自研锁-free 线程池 micropool——主线程参与干活 + 按"根任务"划分工作窃取边界 → 1000 盒子物理 12ms → 8ms。

## 内容要点
- **Rayon 三宗罪**：
  1. 主线程不参与计算，worker 全忙时主线程等待无上界（5ms 的活可能等 20ms）；
  2. 派发即上下文切换浪费；
  3. 工作窃取不区分任务来源：物理等待间隙 worker 可能捡走世界生成任务 → 时间敏感任务被顶掉。
- **Tracy 剖析佐证**：主线程全程 idle；大岛任务被单 worker 扛；worker-3 等掩码计算时跑去跑别的任务。
- **加线程池不行**：主线程还要干别的 → 线程超订 → CPU 过饱和反而卡。
- **micropool 方案**：
  - 外部线程（主线程）亲自参与完成并行迭代器，不 idle；
  - 记录每个任务的「根任务」来源，worker 只窃取同一根任务派生的工作 → 物理/世界生成天然隔离；
  - **无锁调度**：全 atomics。初版 job 树 + RwLock 在 profiler 里全是锁争用橙块 → 推倒重来；
  - 数据结构：固定 job slot 数组 + 原子计数器 fetch_sub 预约工作单元 + 未完成计数归零即完成 + 位压缩的槽位占用掩码（64 个 bool 读一个 u64，高效迭代 0/1 段）；
  - 支持 join 原语、后台任务、并行迭代器（paralite crate）。
- **验证**：Miri 消毒器跑过；Tracy 对比 12ms → 8ms（Rayon 慢 50%）。
- 通用教训：**游戏要延迟优先的调度，不是吞吐优先**。

## 对 gate 的启示
- gate 的 CPU 模拟 per-tick 预算哲学与此完全同源：时间敏感 tick 不允许被后台体素上传/烘焙任务顶掉。gate 内任何 rayon 使用（若有）应套同样纪律：主线程参与 + 任务隔离带。
- micropool 的「根任务掩码」思路可直接抄：gate 把「帧内紧急（模拟/上传）」与「后台（远处细化合并）」用位掩码分区，worker 永不跨区窃取。
- 位压缩掩码迭代法与 gate CellDirs/bitmap 寻址链同款技巧，可复用实现代码模式。
