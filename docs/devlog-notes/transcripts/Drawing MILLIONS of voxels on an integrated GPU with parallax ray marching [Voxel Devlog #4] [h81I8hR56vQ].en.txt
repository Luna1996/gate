voxels with rasterization i had some experience with voxel meshing in the past having done some small scale projects with it before the typical pro approach and the way games like minecraft do things is to generate a mesh based haul for the voxel volume this makes it simple to draw with rasterization however this approach has a major drawback for high voxel counts it creates a large mesh with many triangles this is problematic because too many triangles are hard to store in memory and draw every frame there are some documented techniques to mitigate this the most prominent is greedy meshing sections of voxels and then raymarch within them this would add a little work to the fragment shader but would drastically reduce the overhead necessary to generate mesh buffers and process vertices i call the technique that i ended up using parallax ray marching it's akin to an existing technique known as parallax bump mapping which is used for making normals and bumps on surfaces more realistic you can see it in action on this wikipedia page we want to render a detailed jagged surface without many triangles thus we draw a single flat quad then each frame we simply paint the quad in such a way that it looks 3d changing with relation to perspective this allows the surface to appear real but at a fraction of the processing cost with this idea in hand i whipped up a quick prototype in c sharp the idea was simple for each 8 by eight by eight cube of voxels draw a bounding box in the fragment shader perform ray marching inside the box using the same algorithm that i developed for my previous engine iteration taking the camera's perspective into account use this ray marching technique to decide which voxel is visible inside the bounding box color the surface of the box accordingly in doing so the number of triangles i need to deal with is reduced by an order of magnitude or more while still drawing many voxels here's an early prototype of the technique rendering the stanford bunny here the bounding boxes are turned on so you can actually see the surface which is being rendered having confirmed that this ran well on my integrated gpu i set out to optimize it i implemented the rendering code into my rust engine and designed an algorithm to generate a mesh hall from a voxel octree in the process i applied a key optimization the algorithm only ever generates tight bounding boxes such that there is no unnecessary blank or empty space covered by a bounding box this minimizes the amount of expensive fragment shader invocations and the amount of ray tracing that the gpu has to do after a few seg vaults many graphical glitches and hours of debugging i finished the rendering code i added materials back to the game using some minecraft textures as placeholders depth of the bounding boxes isn't necessarily the same as that of the voxels i cannot rely on the gpu to do this automatically as such i am forced to manually adjust the depth at first this was a big bottleneck because setting the depth in the fragment shader disables a critical gpu optimization the early depth test in the early depth test the gpu won't even invoke the fragment shader for fragments that are behind previously rendered objects however when the fragment shader writes its depth component the gpu cannot know whether it will be behind something and so it must always execute the fragment shader without early z testing my code was very slow ultimately i sidestepped this issue by deferring writing to the depth buffer when drawing voxel objects i draw them normally and also
