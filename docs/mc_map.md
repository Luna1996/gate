# Minecraft 地图流式加载（Greenfield 1.17.1）

把 MC Java 世界的**方块**当成我们的体素世界来流式加载。本文记口径、事实、实测与切片进度。

## 1. 体素口径：1 方块 = 16³ 体素

体素单位取 MC 的**材质分辨率**（16×16）⇒ 一个方块 = 16³ 体素（我们一个体素 = 1/16 方块）。
由此得到一条**精确对齐**（不是近似）：

```text
我们的 chunk 边长 = 256 体素 = 256/16 = 16 方块 = MC 的**一个 chunk-section**
我们的 chunk 坐标 = (chunkX, sectionY, chunkZ)          // floor(方块/16) == floor(体素/256)
```

⇒ M5/M6/M8 那套流式环（`ChunkSource` + 窗口跟相机 + 射线请求驱动 + LRU + 多 volume）**原样可用**：
`ChunkSource::produce` 只要做"我们的一块 = MC 的一个 section"这一个翻译，**无缩放、无偏移**。
一个 section = 5.12 m（1 体素 = 2 cm），与 `infinite_cubes` 的 chunk 同尺寸。

高度：1.17 的世界高 0..255 ⇒ 16 个 section = 我们的 16 层 chunk。

## 4. 代码结构与依赖

| 文件 | 职责 | 状态 |
|---|---|---|
| `mc/world.rs` | 存档读取（region 索引 / 解压 / NBT → 区块结构）＋ 区块 LRU | **已落地** |
| `mc/assets.rs` | blockstate / model JSON + 贴图 PNG 的读取与缓存 | **已落地** |
| `mc/model.rs` | blockstate → 元素盒（`variants` / `multipart` / `parent` / 贴图变量 / 缺省 uv） | **已落地** |
| `mc/voxel.rs` | 元素盒 → 16³ 逐 texel 色 → **8 cm 写入计划**；材质与染色启发式 | **已落地** |
| `mc/material.rs` | 逐 texel 颜色 → 调色板槽（内容去重 + 颜色量化 + 溢出回退） | **已落地** |
| `mc/source.rs` | `ChunkSource`：一块 = 一个 section；`Detail` 的四档落地 | **已落地** |
| `mc/mod.rs` | 世界注册（`scene::build_world` / 菜单 / `Streaming` 接线）+ 端到端冒烟 | **已落地** |

**格式解析全部走现成 crate**（不自造轮子）：

| 环节 | 谁做 |
|---|---|
| NBT 反序列化 | `fastnbt`（serde） |
| region 4 KB 索引、扇区载荷、压缩（zlib / gzip / lz4 / 裸） | `fastanvil::Region::read_chunk` |
| `BlockStates` 位打包展开（1.15 跨长 / 1.16 留白两种） | `fastanvil::expand_blockstates` |
| `level.dat`（gzip+NBT）的出生点 | `flate2` + `fastnbt` |
| 贴图 PNG（灰度 / 调色板 / 16 位统一成 RGBA8） | `png`（`Transformations::normalize_to_color8`） |
| blockstate / model 的 JSON | `serde_json` |

**为什么不用 `fastanvil::pre18::JavaChunk`**：它把方块压成 `fastanvil::Block`，而 `Block` 只公开
`name()` / `encoded_description()`，后者**有意丢掉 `waterlogged` 与 `powered` 两个属性**（服务于
fastanvil 自己的彩色渲染）。而 `variants` 的条件匹配要按属性找形状（台阶朝向、楼梯形状、门、红石灯）
⇒ 属性必须原样保留，所以用 `fastnbt` 自定一层薄结构（fastanvil 文档的推荐用法）。

`mc/model.rs` 与 `mc/voxel.rs` 没有同类 crate 可替：MC 的资源包模型格式（`variants` 条件 /
`parent` 继承 / 贴图变量 / `elements` + 显式 uv / 块级旋转）在 Rust 生态里没有成熟实现，
`nucleation` 那类工程是自成一体的（同时含网格化与 GPU 渲染），与本仓的"体素化 + 自己的 DDA"不通用。

## 5. 形状与颜色的规则（首版覆盖）

- `variants`：键 = `性质=值` 用 `,` 连（AND）、值可用 `|` 给候选；按方块的 `Properties` 匹配；
- `multipart`：`when` 可为字符串、`{性质: 值}`、或 `{"OR": [...]}`（数组元素是对象）；
- `parent` 继承链：**父在前、子覆盖**（子有 `elements` 就整段替换，`textures` 逐键覆盖）；
- 贴图变量 `#all` 这类按 `textures` 表逐跳解析（深度上限 8，防环）；
- 面的 uv：缺省按元素盒六个面推（与 MC `FaceBakery` 同一套公式），显式 uv 原样取；
- 块级旋转（`x`/`y`）：在**体素层面**整体旋转（90° 的倍数 ⇒ 格到格、无插值），顺序 = **先 x 后 y**
  （用 `oak_log` 的 `axis=x` = `x:90,y:90` 与 `stairs` 的 `facing=east` = 无旋转反推出来的）；
- 逐格上色：取**最近的面**的 texel；同时贴两个面时按 `up > down > west > east > north > south`；
  贴不到任何面 = 元素内部 ⇒ 取该元素各面贴图均色（内部不可见，均色还能让整砖合并）；
- texel 的 α = 0 ⇒ **不写**（挖空：树叶的洞、玻璃中央）；`0 < α < 255` 当半透（玻璃走 transmission）；
- `tintindex` 存在时按方块名取**固定生物群系色**（草 `#91BD59` / 叶 `#77AB2F` / 水 `#3F76E4`，
  云杉与白桦用各自的原版色）—— **不读 `Biomes`**；
- 材质参数（粗糙度 / 自发光 / 透射 / 金属度）按**方块名**启发式给（`glowstone`/`torch`/`*_lamp[lit=true]`
  自发光、`*glass`/`*_pane` 透射、`*_ore`/含 `iron|gold|copper` 的金属、其余按粗糙石材）；
- 缺 blockstate 或形状整段缺失（水、熔岩这类流体）⇒ 兜底"整块 + 同名贴图"（`block/<名>`，退一步 `_still`）。

**不覆盖**（首版明确的取舍）：元素自带的 `rotation`（植物的 45° 交叉面退化成轴对齐薄片）、`uvlock`、
`display`、`ambientocclusion`、面内 `rotation` 的 90/270 符号（按 180 的公式推的，可能是镜像）。

## 6. 实测：为什么"逐 texel"不可用（重要）

**结论：MC 的"逐 texel 上色"在现有树结构下不可用，最终取 8 cm 档（每 4³ 体素一个代表色）。**

`real_map_produce`（出生点 chunk，`Detail::Full`，7 层含 3 层满实体）：

| 颜色量化 | 稳态产出 | 树大小 | 备注 |
|---|---|---|---|
| 8 位（原样） | **78 ms/层** | **20 832 KB/层** | 逐 texel（每个 `4³` 砖都是值表） |
| 5 位（当前默认） | **0.5 ms/层** | **74 KB/层** | 8 cm 档 |

原因是**结构性的**，颜色量化救不了：一个方块的表面层有 56 个 `4³` 砖，每个砖横跨 4×4 个 texel
⇒ 砖内必然多色 ⇒ 每个砖都要一张 4³ 值表（CPU 128 B / wire 24 B）。4096 个方块 = 2600 万个砖，
一层就是 20 MB 级、产出 80 ms 级；而池预算按 1 MiB/块折算 ⇒ 只能装几十块，"视距"退化成几步。

8 cm 档把"每砖一个代表色"当作写入单位：砖内同色 ⇒ 值表消失、能并进父层；一个方块在
**石/陶土/混凝土这类单色块**上收缩成**一条 `extent 16` 的写**（产出 0.5 ms/层、树 74 KB/层）。
观感上贴图的色块变化仍保留（4×4 texel 的多数色），只是细节粒度从 2 cm 变成 8 cm。

颜色量化（每通道 5 位，默认）另有两个好处：调色板槽从 4317 → **716**（贴图噪点被并成同色），
冷启动的建计划耗时 31 → 10 ms。溢出回退（槽满后按 8 级/通道找最近色）实测**从未触发**。

出生点 chunk `y=4` 的颜色抽样（每 4 格一次，`real_map_produce` 输出）—— 贴图确实被用上了：

```text
槽 135 × 9856  [216,216,216]   white_terracotta     槽 168 × 4864  [80,64,48]   birch_planks（棕）
槽  90 × 7326  [120,120,120]   stone（灰）          槽  92 × 4805  [104,104,96] stone_bricks
槽  88 × 5248  [112,112,112]   stone（深）          槽 110 × 4352  [200,200,192] 浅色石材
```

## 7. 接进流式世界（`Detail` 的落地）

| `Detail` | 粒度 | 每方块写几次 | 谁要它 |
|---|---|---|---|
| `Full` / `Fine` | `4³` 体素（8 cm） | 1（单色块）..64 | 射线请求的 level 0/1、半径环 15..58 chunk |
| `Coarse` | 整块（16） | 1 | 半径环 59..233 chunk、请求 level 1 |
| `Wide` / `Chunk` | `4³` / 整层个方块 | 1 / 每 64 个方块 | 更远的请求 |

- 生产源通过 `Streaming::source` 注入（`scene::build_world` 里设），流式环发现源变了就重建 worker 池；
- 槽位由 worker 认领 ⇒ 主线程按 `ChunkSource::palette_log` 的游标把条目装进**各 volume** 的调色板
  （每帧一次、在**挂载之前**；换世界 / 换源时游标清零重放）；
- 建世界**不预铺任何 chunk**（一层最多 4096 次模型体素化，同步铺会卡住启动）⇒ 内容全交给流式环；
- 相机的默认机位在出生点（`level.dat`），存档姿态若离出生点 > 500 m 也回退到出生点（免得上一个世界的
  机位把相机丢在空气里）；世界代码**只设生产源**（`Streaming::set_source`）。
- **流式旋钮（半径 / 帧额 / 预算）由 DebugMenu「世界」页独占**：`apply_initial_state` 会把菜单的最终
  控件值重放成 `MenuActionEvent`（在 `setup` 之后一帧执行）⇒ 世界代码写它们会被当场覆盖。
  这一条是实测发现的：原先的 `Streaming::tune_for_mc`（`coarse_radius=4 / coarse_height=2`）被菜单里
  上一轮的 8 / 6 顶掉，而"环 8×6 = 3757 块候选"正是常驻集涨到 1758 块（≈90 MB）的原因
  （`DEMAND[batch …；环 8×6；常驻 …]`）。所以 `tune_for_mc` 已删除，改调参只能走菜单。
- **远场级（M8）已接**：远场每格代表 `scale` 个方块，走 [`mc::summary`](../gate-app/src/mc/summary.rs)
  的**摘要金字塔**（每 section 一份代表色 + 每 `4³` 方块一份细格），按"格中心那一列"采样
  ⇒ L1/L2 每块读 16 / 256 个 chunk 列，L3 每块读 256 个（详见 §8.3）。`VolumeGrid` 的
  `attach_far` 标记由 `mc::build` 与 `build_infinite_cubes` 共同设置，`scene.rs` 按它挂三级远场。

实测（`GATE_LOG=info,gate_app=debug`，出生点附近）：

```text
MC 地图 ...，出生点体素 [1840, 1136, -32]；资产 ...；窗口 ±32 chunk（±164 m）
STEP 2 world mc_map instances=1 written=0 dropped=0 3.25ms
MC 首个 section 产出（chunk -14,2,35）：调色板 155 槽（溢出回退 0 次）、区块缓存 (3, 0)、缺失资产 1 个
MC section 累计产出 256 / 512 / 768 / 1024 / 1280        ← 约 900 section/s（3 个 worker）
RESID[resident 1502 91770KB install … evict 0]           ← 收敛后 0 换出、0 请求
```

## 8. 已知问题与待办

### 8.1 已解决：空 section 的请求洪水（"空"与"没加载"必须分开）

**症状**：城里大多数 section 是空气 ⇒ `produce` 返回 `None` ⇒ 那一块不进 `b_struct`。而索引条目用
一个 `0` 同时表示"还没加载"与"是空的"，shader 分不出来 ⇒ 射线在**永远装不上东西**的空 chunk 上
反复发请求。实测（出生点默认机位，相机自己那一层就是空的）：

```text
REQ[去重 4 chunk、最热 v0(5,6,-2)×1030603 v0(8,6,-2)×13243 …）；本窗口 6876834 条、超容丢失 5828258]
```

最热一块 **103 万票/窗**、请求环（1 M 字）被这一块整圈覆盖 ⇒ **真正的请求全被挤掉**（ray-guided
逐块加载事实上失效），且每秒数百万次原子写砸在同一个字上。`infinite_cubes` 不会遇到这个问题
（`every_chunk_has_content` 是它的前提）。

**修法**：让"已知空"成为索引里的一等状态（跨 4 层，没有新 binding、没有新 buffer）：

| 层 | 改动 |
|---|---|
| `gate_voxel::VolumeGrid` | `empty_chunks` + `mark_empty_chunk` + `empty_seq`（与 `stream_window` 同类的"流式提示"） |
| `gate_app::infinite_cubes` | 源产出 `None` 时除了记自己的 `st.empty`，同时 `grid.mark_empty_chunk(cc)` |
| `gate_render::brickmap::builder` | 索引条目写哨兵 `INDEX_ENTRY_EMPTY`（u32::MAX）：新建 / 新记 / **窗口平移后重打**（平移会把索引区整体清零）；`note_empty` 跳过已常驻的块；`install_blob` 写真地址时自然覆盖 |
| `gate_render::brickmap::upload` | `plan_residency` 的 ①' 按 `empty_seq` 把新增空块同步给 builder（**逐卷**：MC 的远场级同样会产出 `None`） |
| `trace.wesl` / `brickmap.wesl` | 请求闸门只看 `entry == 0`（`has_tree = entry != 0 && entry != INDEX_ENTRY_EMPTY`）；遍历把两种都当空气 |
| `common.wesl` + `consts.rs` + `wesl_consts.rs` | 哨兵常量两侧各一份，启动时**逐字核对**（不等 = 把哨兵当树块地址解引用） |

**结果**（同一机位、同一时长）：

```text
REQ[去重 4 chunk、取 4 条（最热 v0(14,5,-1)×4251 v0(14,5,0)×2507 …）；本窗口 9592 条、超容丢失 0]
```

每窗请求 687 万 → **9592 条**（−99.86%）、超容丢失 583 万 → **0**、最热一块 103 万票 → 4251 票。
而且请求**真的被消费**了：`DEMAND[batch 4（请求 4）] → STREAM[gen4]`（常驻 1758 → 1762）——
ray-guided 逐块加载从"被洪水打满"变成"正常工作"。单测见
`brickmap::builder::tests::empty_chunk_marker_is_written_and_reapplied`。

**同一机制覆盖到静态世界**（`.vox`）：那种世界**没有生产源**（`stream_chunks` 不跑）⇒ 渲染窗口里
"没有内容"就是**确定是空**，不必等"产出过 `None`"（`plan_residency` ①″，上限 64K 窗口槽）。
实测 `nuke.vox`：请求 **2 831 521 条/窗、超容丢失 1 782 945、最热一块 157 707 票 → 0 条**
（补标 318/400 槽）。流式世界**不能**这么推（那块可能正在产出）。

哨兵同步按 `VolumeGrid::empty_log`（追加日志）的**游标**只处理新增块：早先按 `HashSet` 全量重扫，
爬坡期逐块触发 ⇒ O(n²)（一轮填充 2000 块 ≈ 200 万次哈希探测的白扫）。

### 8.2 待办

- 逐 texel（2 cm）若要做，得先解决树的"每砖值表"结构（例如按方块状态预存 16³ 模板 + block 级间接），
  不是加内存能解决的（见 §6）。
- 缺失资产 19 个（原版 `barrier` / `light` 这类不可见方块，以及资源包里没有的旗帜、墙上告示牌）
  ⇒ 这些方块**不产出**（skip），`assets.missing_names()` 可查。
- 面内 `rotation` 的 90/270 符号、元素自带 `rotation`（45° 交叉面）、`uvlock` 未实现。
- 生物群系染色取固定色（不读 `Biomes`）；材质参数是按名字的启发式，不读方块表。
- **远场的填充速率**：L2/L3 一块要读 256 个 chunk 列 —— **已由离线粗粒度世界解决**（见 §8.4）：
  实测一块 `0.2 ms`（原来 `1 s` 级）。现在的约束换成了"装的时候帧稳不稳"（见 §8.5）。

### 8.3 已解决：远场级（M8）的 MC 通路

**问题**：远场 chunk 覆盖 `16·scale` 个方块每轴，逐块采样时 L3 的一个 chunk 要碰 `64³` 个 MC chunk，
不可行。

**做法**（[`mc::summary`](../gate-app/src/mc/summary.rs)）：**摘要金字塔**，按级降采样，每格只读
"它需要的那一个 chunk 列"：

| 级 | `scale` | 一格（方块） | 采样 | 每块读 chunk 列 |
|---|---|---|---|---|
| L1 | 4 | 4 | 所在 section 的 `4³` 细格（每节预算一次、64 格） | 16 |
| L2 | 16 | 16 | 格 = 一个 section ⇒ 该 section 的代表色 | 256 |
| L3 | 64 | 64 | **只读格中心那一列**（1/16 的采样面） | 256 |

摘要按 section 缓存（`Sec`：64 个细格 + 整节代表色 + 实体数，~200 B/节）。格的判据与主世界粗档同源：
**实体占比 ≥ 1/8 才写**（否则街道 / 空地会糊成实心）；色 = **表面色** —— 每一级都取"最上面那一层
**够实**（实体 ≥ 半层）的子格"的多数非空气色（[`voxel::rep_of_surface`](../gate-app/src/mc/voxel.rs)），
**不是整格多数色**：后者会把"一层水面 / 草皮压厚基座"的格染成基座（水面 → 沙/石、草地 → 土），而远场
一格在画面上就是成片的方块 ⇒ 与近场之间出现成片色差、边界是格对齐的直角。没有"够实"的层（薄墙 /
竖直面）时退回旧的整格多数色 ⇒ 只有"薄表面压厚基座"那一类会变。

**实测**（`real_map_far_produce`，出生点，`--ignored --nocapture`）：

```text
L1 scale 4：chunk (1,1,-1) ⇒ 1450/4096 格非空、树 5984 字 = 23.4 KB、3846.2 ms（新增缓存区块 16）
L2 scale 16：chunk (0,0,-1) ⇒ 1444/4096 格非空、树 2870 字 = 11.2 KB、2473.5 ms（新增缓存区块 256）
L3 scale 64：chunk (0,0,0)  ⇒  450/4096 格非空、树 1915 字 =  7.5 KB、 480.8 ms（新增缓存区块 256）
```

**读入的 chunk 列数与上表逐字吻合**（16 / 256 / 256）。耗时里前两级的绝大部分是**首次建方块计划**
（`plan_for` 的 16³ 栅格化，按状态缓存）—— L3 计划已热，256 列 **481 ms** ⇒ 稳态约 **1.9 ms/chunk 列**，
即 L2/L3 各约 **0.5 s/块**。块本身很小（7.5–23 KB），所以 GPU 侧的三级远场合计只占几 MB。

**接线**：`mc::build` 置 `attach_far` ⇒ `scene.rs` 调 `attach_far_levels_mc`（**只挂 volume、不装
调色板**：MC 的槽号由 worker 认领，靠 `palette_log` 重放填进**所有** volume）。

实跑（`GATE_BENCH=orbit`，60 s）：

```text
FAR L1 scale 4（1 级体素 = 4 世界体素）覆盖 ±0.66km；… 格 16 级体素 = 1.28m
FAR L2 scale 16 … 覆盖 ±2.62km；…
FAR L3 scale 64 … 覆盖 ±10.49km；…
STREAM[v1 far gen… chunks 92] / STREAM[v2 far … 40]        ← L1/L2 在涨
RESID[resident 2048 97672KB install 0 evict 4 | 远场 131块/装 0 evict 0]   ← 远场已在 GPU 上
EMPTY[vol1] 哨兵 +2（已知空共 686）… EMPTY[vol3] 哨兵 +2（已知空共 783）
FPS[1s] 60 低 57 高 63                                     ← vsync on，未掉帧
```

**L3 几乎不涨**（`DEMAND[v3 far] batch 151（全为请求）` 但常驻恒 0）：这不是没接上，而是
**L2 挡住了射线** —— 城市半径约 2.8 km，L2 已覆盖 ±2.6 km ⇒ 能走到 L3 的只有穿过 L2 空隙的少数射线，
而它们指向的 L3 格基本在城市之外（空气）。真要 10 km 的**有料**远场，得先让 L2 铺满（§8.2 的速率问题）。

### 8.4 已实现：离线粗粒度世界（`mc::lod`）

**问题**：远场那块 256 次列读要的东西很小（每节一个代表色 + 实体数），却是"按需读存档"这条路的
全部成本 ⇒ 铺满 ±2.6 km 要几分钟。

**做法**：把整张图**离线算一次**存盘（[`mc::lod`](../gate-app/src/mc/lod.rs)），远场 `scale ≥ 16`
改从这份文件内存采样：

| 环节 | 口径 |
|---|---|
| 文件 | `data/lod/<世界名>.lod`：头（版本 / 地图指纹 / 列范围）+ 方块状态名表 + 逐列 RLE 的节摘要 |
| 一格 | 一个 section（16 方块）：`solid` = 非空气方块数、`rep` = **最上面那一层有料的方块**里的多数状态（键，表面色） |
| 覆盖范围 | 由 `region/` 里**实际存在**的文件定（Greenfield：34×34 region ⇒ 1088² 列） |
| 装载 | 指纹（地图路径 + `level.dat` 大小/mtime）不符即作废；名字按键重查 `plan_for` → 代表色 |
| 构建入口 | DebugMenu「世界」页 →「构建 LOD」（后台线程 + 进度日志，完成即**热装**，无需重启） |

**实测**（`real_map_build_lod`，出生点附近的远场块）：

```text
LOD 文件：1183744 列、1384968 节、名字 329 个、12.1 MB、5.6 s（211531 列/s）
L2 scale 16：LOD 0.1 ms vs Anvil 1071.7 ms ⇒ 7290×；逐格：同色 1340、异色 104、单边有料 1、都空 2651
L3 scale 64：LOD 1.0 ms vs Anvil  486.5 ms ⇒  475×；逐格：同色  387、异色  61、单边有料 20、都空 3628
```

两处口径差（替代关系，不是叠加）：`rep`（**表面**色：最上面那一层有料的方块里的多数）按**方块**取
（`summary` 先按 `4³` 格折一层）；`scale > 16` 时**采满格内 `n³` 个节**（再取最上面那一层有料的节），
而 `summary` 只采格中心那一列（当初为省列读，现在没有理由再丢信息）。

**口径一变，旧文件立即作废**（`lod::FORMAT_TAG` 进指纹 ⇒ `load` 返回 `None`，远场回落到按需读 Anvil
直到重建）：这一刀把 `FORMAT_TAG` 推到 **v4**（代表色改取表面）⇒ 跑一次 DebugMenu「构建 LOD」即可
（Greenfield 全图约 5.6 s）。

**应用级**（`GATE_BENCH=orbit`，同机位 80 s）：远场常驻 `951 → 1578` 块、`gen` L1 `1952 → 2412`、
L2 `1066 → 1114`；近场段产率不变（它是需求驱动的）。

### 8.5 需求模型：预载圆盘（已实现）与剩下的**安装积压**

**症状**：每次转动视角，新朝向的区块要几秒才补上（"一转就看到加载"）。

**成因**：装载 100% 由射线请求驱动，而请求的语义是"**我已经看过、发现它缺**"⇒ 永远落后于视线；
旧版的预载是"前向锥 + 身后一条"，侧向 40–160 m 整个落在锥外。池满时 `fill = 0` 还会把预载**整段
停掉**，只剩请求在补。

**改动**（[`plan_generation`](../gate-app/src/infinite_cubes.rs) / `plan_generation_far`）：

| 口径 | 旧 | 新 |
|---|---|---|
| 近场候选集 | 前向锥（±`coarse_radius` 侧向） | **XZ 圆盘**（`coarse_radius` × `coarse_height`）—— 朝向无关 |
| 远场候选集 | 无（只由请求驱动） | **球壳**（`FAR_PRELOAD_INNER`=8 之外、`FAR_PRELOAD_OUTER`=30 之内，竖向 ±8） |
| 排序 | 近处盒 → 视野锥 → 距离 | **欧氏距离**（主序，转身不重排）→ 视野内 → 坐标 |
| 预算 | `fill` = 池里的空位（池满即 0） | `cap` = 目标常驻块数，**请求与预载共用** |
| 预载的"够不够" | 按距离定档 | **只看存在性**（细化仍由射线报 level） |

实测（`GATE_BENCH=orbit`，同机位 80 s）：近场产出 **171 → 262 段/s**、远场 `gen` L1 2412 → 2830、
L2 1114 → 1921、远场常驻 1578 → 2070 块。

**留下的问题（下一步的靶子）**：`RESID[install 8]` 长期顶在 `max_install_per_frame`。拆开看是两个
**真 bug**（都已修）：

| bug | 症状 | 修法 |
|---|---|---|
| 账目①把每个新挂载的块都记成 `BRICK_FACTOR` | 每块白付一次降级重装：40 s 内 **6952 次** | 流式世界改记**距离阶梯**给出的档（CPU 侧 `detail_at` 与 GPU 侧 `want_level` 是同一把尺）⇒ 降级 **0** |
| 需求④的距离阶梯把射线**细化过**的块又粗化回去 | 与射线打架：40 s 内升级 1666 / 降级 1574（成对） | 流式世界**只细化不粗化**（`want_level(..).min(cur)`）⇒ 降级 **0** |

**根因（第三个，也是帧时的真凶）：远场树区预留按错了世界。**
`UPLOAD[full]` 是"某个 volume 的 `b_struct` **长度**变了 ⇒ 整份拼一遍再上传"的降级路径，而它
**每装一块触发一次**。诊断行（`BASES 漂移`）直接指名：

```text
v0 树区 17809355 字/预留 0（1568 块） | v1 树区 6494286 字/预留 4194304（1125 块） | v2 … | v3 …
```

`v1`（L1 远场）**超出预留 55%**。原因：`FAR_RESERVE_WORDS_PER_CHUNK = 2048` 是按 `infinite_cubes`
的远场块（1219–1463 字）定的，而 **MC 的 L1 远场块实测 5773 字/块（4×）** ⇒ 预留区迅速用尽，此后
**每装一块长度都长一次** ⇒ 35 s 内 **121 次全量快照**、帧时 16.7 → 45 ms。

**修法**（[`BrickMapBuilder::grow_region`](../gate-render/src/brickmap/builder.rs)）：预留型 volume
（远场级）的空闲段一旦用完，就**把长度一次顶到 `region_chunks × 实测每块字数`** 并把新段登记为空闲
（`alloc_block` 相应改成"重试空闲表"而不是沿用旧长度自行 `resize`）。之后长度恒定 ⇒ 全量快照只在
第一次发生。

**实测**（`GATE_BENCH=orbit`，90 s，同机位）：

| | 修前 | 修后 |
|---|---|---|
| `BASES 漂移` / `UPLOAD[full]` | 121 次 / 35 s | **2 次**（初始 + L1 顶位一次） |
| 帧周期 | 16.7 → **45 ms**（跑着跑着劣化） | **16.70 ms 中位**（= vsync 地板），>18 ms 仅 3/87 |
| FPS | 22 | **60**（最低 41 是启动爬坡） |

### 8.7 两个排查"距离环异常"的诊断（DebugMenu「世界」页）

**症状**：某一**距离带**上的楼集体变成骨架 / 透空（近处与更远处都正常）。

**为什么需要专用诊断**：这个症状的可能来源横跨四层（几何 LOD 的填充规则 / 分壳裁剪的覆盖带 /
流式装载没填满 / GPU 侧 proxy 塌缩），而下面这几条路经**代码阅读已全部排除**：

| 被否证的假设 | 否证方式 |
|---|---|
| 粗档 1/8 填充规则删掉了薄墙 | 实测被删的 149 个节只承担**可见表面的 2.5%** —— 删的是埋在里面的，不足以造成"中空" |
| GPU 侧 `proxy()` 塌成代表色会挖空 | [`ChunkTree::rep_of`](../gate-voxel/src/chunk_tree.rs) 对 Split 节点按子块序取第一个非空子树色、**只有全空才返回空气**；`node.mask` / `palette` 原样保留 ⇒ 只会固化膨胀 |
| 叶级 LOD 早停把砖判成空气 | `leaf_rep_palette` 里 `if v == 0 { continue; }` —— **空气不参与计票**，有实心体素就返回实心色 |

所以只剩"那一带**根本没有几何**"，而"没有几何"又分"装载没填满"与"分壳把它跳过了"。两个诊断就是
为了一刀切开这两者：

| 诊断 | 位置 | 用法 |
|---|---|---|
| **远场级数**（0..3 滑杆） | `Streaming::far_levels_max`：`vol > 本值` 的远场级**整卷停用**（不产出、不挂载、已装的卸载） | 转到异常那一圈，从右往左调 —— 异常在哪一级被关掉时消失，就是那一级 |
| **卷着色**（开关） | `BaseSettings::vol_tint`（uniform `base_flags` 的 bit2）：主射线命中按所属 volume 上假色 —— **主世界=绿 / L1=红 / L2=蓝 / L3=黄**，天空近黑 | 直接看那一圈的楼是**什么颜色** ⇒ 一眼看出它归哪一级，且洞是谁留下的（旁边是什么色） |

卷着色**不需要给 `WorldHit` 加字段**：`WorldHit` 已有 `palette_base`，而每个 volume 的 palette 段
各有自己的基址 ⇒ 用 `grid_descs[i].palette_base` 反查出卷号（[`vol_tint_color`](../assets/shaders/voxel_raytrace/world.wesl)）。

实测（`GATE_BENCH=orbit`）：诊断全关时 **MAIN 1.01 ms/帧、帧周期 16.70 ms 中位、FPS 59**（零回归）；
滑杆调到 `1` 时 `v2 far gen → 8`（仅生效前的 2 帧）、`v3 → 0`，确认整卷真的停用了。

### 8.6 帧时账（`GATE_LOG=gate=debug` 的四行）

```text
MAIN 主世界调度      1.00 ms/帧（最大 2.09）   ← 含 STREAM 0.43
RESID 常驻调度       0.88 ms/帧                ← 渲染世界 extract
REQ 读回+合并        0.57 ms/帧
STREAM 流式装载      0.43 ms/帧
RENDER 帧周期       16.70 ms：渲染世界自身 0.50 ms，等别处 16.2 ms
```

⇒ **整帧的工作量约 3 ms**（主世界 1.0 + extract/prepare ≈1.5 + 渲染图 0.5），其余 13.7 ms 是 **60 Hz
present 的等待**。注意 `等别处` 是个大杂烩（主世界 + extract + prepare + submit + present），
只看它会把"被 vsync 节流"误读成"卡在某个系统"——所以要先把 `MAIN` 那一行量出来才谈得上归因。

CONSTRAINT: `PresentMode::Fifo` + **窗口化**（Windows 下 `Immediate` 无 tearing 许可时同样被节流到
刷新率）⇒ 想看到 >60 fps 的**呈现**帧率必须换全屏/开 tearing，那是显示配置不是本工程的问题。
本工程的验收口径因此是**工作量 < 10 ms**（当前 ~3 ms，余量 3×）。

### 8.8 半径阶梯：把"中空"换成"级边界对齐"（A'）

**靶子**（§8.7 的结论）：L1 常驻数顶死容量且抖动（`gen/unload` 成对），1536 块散在 r=0..29 上
⇒ 覆盖 ~6% ⇒ 楼的外墙块常没被抽中，射线穿过去打到内表面（仍是 L1，红色）⇒ "空心楼"。

**改法**（[`infinite_cubes.rs`](../gate-app/src/infinite_cubes.rs)）：每级**只填自己那一整圈**，并把
**窗口水平半宽缩到那一圈的外缘** —— 分壳裁剪读的是 descriptor 的世界 AABB，而那个 AABB 按窗口算，
所以"级边界"就是这个窗口：

| 口径 | 旧 | 新 |
|---|---|---|
| 窗口 | 三级都 64³ chunk（名义 ±655 m / 2.6 km / 10.5 km） | 水平半宽 = `r_out + 1`，竖向仍 64 |
| 预载 | 球壳 `FAR_PRELOAD_INNER`=8 起、`FAR_PRELOAD_OUTER`=30 止，被 `budget` 截断 | `far_radius_ladder` 反算的 `r_in..=r_out`（**完整的一圈**，容量放不下就不开这一级） |
| 环带成本 | 按枚举范围 17 层算 | 按**内容层数** `FAR_CONTENT_LAYERS` 算（标定过程见下一段） |
| 级间接力 | 靠名义 AABB | 下一级内圈 = 上级外圈 ÷ 4（取 floor：重叠无害，留缝 = 洞） |

**标定 `FAR_CONTENT_LAYERS`**（每环块数 = `8·层数·r`，层数是唯一可调项）：先用理论上界
`[8, 2, 1]` 跑一轮，得到各级的**实测每环块数** = `常驻数 / Σ r`：

| 级 | 实测 | 理论（`[8,2,1]`） | 高估 |
|---|---|---|---|
| L1 | **13.7·r**（r8..12 共 683 块） | 64·r | 4.7× |
| L2 | **5.1·r**（r2..19 共 969 块） | 16·r | 3.1× |
| L3 | **1.4·r**（r4..7 共 31 块，城市到此为止 ⇒ 下界） | 8·r | ≥5.7× |

理论值假设"每个水平格、每一层都有内容"，而内容只集中在少数几层 ⇒ 高估 3–6 倍，把整级压在很短的
半径里（L1 只到 246 m）。取**实测 × 约 1.6–1.8 的余量** ⇒ `[3, 1, 1]`：阶梯必须仍是一个**上界**
（外圈填不满 = 洞回来），余量就是替"更密的图"买的。

**实测**（`GATE_BENCH=orbit`，3.5 min，同机位，`FAR_POOL_CHUNKS` = 4096）：

```text
                           上界 [8,2,1]                        标定 [3,1,1]
FAR L1 格 1.28m   窗口 24×64×24、r8..11  ← 245.8 m   窗口 36×64×36、r8..17  ← 368.6 m
FAR L2 格 5.12m   窗口 40×64×40、r2..19  ← 1.64 km   窗口 56×64×56、r4..27  ← 2.29 km
FAR L3 格 20.48m  窗口 56×64×56、r4..27  ← 9.18 km   窗口 56×64×56、r6..27  ← 9.18 km
STREAM[v1 far …]  gen1 unload 0 chunks  683 rmax 12   gen1 unload 0 chunks 2056 rmax 18
STREAM[v2 far …]  gen1 unload 0 chunks  969 rmax 19   gen1 unload 0 chunks 1107 rmax 26
STREAM[v3 far …]  gen1 unload 0 chunks   31 rmax  7   gen1 unload 0 chunks   12 rmax  7
RESID[远场 …]     1683 块 / 装 0 evict 0              3175 块 / 装 0 evict 0
BASES 漂移 / UPLOAD[full]：各 1–2 次（都在启动）
```

**帧时**（把 `video/vsync` 关掉才量得到真值，`GATE_BENCH=orbit` 3 min，3175 块远场）：

```text
RENDER 帧周期 n=424：min 2.9 / p25 5.6 / 中位 5.8 / p75 7.3 / p95 8.4 ms，>10 ms **仅 1 次**
                     （16.2 ms，落在启动填充期）
MAIN 1.31 + RESID 0.64 + REQ 0.48 + STREAM 0.72 = 3.15 ms/帧（CPU 侧）
```

⇒ **洞的来源（散点覆盖）消失**：两轮都满足 `unload 0` + `evict 0` + `rmax = r_out`（旧读数：
`rmax 29`、`gen/unload` 成对、常驻顶死 1536）。标定后 L1 的 1.28 m 档从 246 m 推到 **369 m**、
L2 到 **2.29 km**，代价是远场常驻 1683 → 3175 块、中位帧时 5.8 ms（余量仍有 ~4 ms）。

**留下的边界**：再往外推只有两条路 —— ① 继续放池（`FAR_POOL_CHUNKS` ↑）：单位数直接换帧时；
② **B：把载入单元本身放大**（远场 chunk 每轴 ×4、格不变）⇒ 同一片几何的单位数 ÷16～46，帧时与
树区开销一起降。B 不是局部改动：chunk 边长目前**不是** per-volume 字段（`CHUNK_SIZE` 在
`gate-voxel::coords` / `gate-render::brickmap::wire` / `dda.rs` / `common.wesl` 四处镜像，
97 个使用点），树是 4 层定深（`MAX_LEVEL`/`LEVEL_EXTENT: [i32; 5]`/`NodePath.ids` 定长），
shader 的层次 DDA 按"4 层、根 256"写死（`array<Brick, 4u>`、`shift = 8-(level+1)*2`），

### 8.9 细档进离线 LOD（A'2）+ B 的收益重估

**A'2 的目标**：L1（1.28 m 格）至今按需读 Anvil（实测 **87–174 ms/块**，2056 块铺满要一两分钟），
是"加载太慢"的直接来源；而离线 LOD 只服务 `scale ≥ 16`（一格 = 一个节）。

**改法**：LOD 文件升到 **v2**，每节多存一份 `4³` **细格**（[`FINE_CELL`] = 4 方块，RLE：
`(u16 名字下标, u8 连续个数)`，长度和恰为 64）。采样接口相应从"传 `scale`"改成**传格的方块边长**
（`cell_blocks`）—— 格的边长 = `FAR_GRAIN·scale/16`，在 `FAR_GRAIN = 16` 时数值上等于 `scale`，
所以这步是纯重构，但它把"单元有多粗"与"格有多大"解耦（B 要的正是这个解耦）。
另一处必须跟着改的：**节该不该留**。原来的门槛是整节实体 ≥ 1/8，而薄墙（16×16 的墙 = 6%）会被
整节判空、它的细格却够实体 ⇒ 细档会凭空少几何。现在"整节够实体**或**有任一细格够实体"就留。

**实测**（`real_map_build_lod`，`GATE_LOD_REAL=1` 写真实文件名）：

| | 改前 | 改后 |
|---|---|---|
| 文件 | 1183744 列、1384968 节、**名字 329**、**12.6 MB**、5.6 s | 同列数、**1438880 节**（+54k 薄墙节）、**名字 9325**、**35.9 MB**、7.1 s |
| L1 `scale 4` | 不走 LOD（Anvil **87.1 ms/块**） | LOD **0.2 ms/块**（**469×**）、树 5984 字（与 Anvil **逐字相同**） |
| 逐格比色 | — | 同色 1287、异色 163、**单边有料 0**、都空 2646 |

⇒ 单边 0 = 两条路对"哪些格是空的"完全一致（细格门槛对齐的效果）；163 个异色来自平手取色的规则
（LOD 按节内调色板序、`summary` 按全局槽号）。名字从 329 涨到 9325 是因为要认领**每个**出现过的
状态（细格的多数色可能是任意状态），812 个没认领到槽（缺资产）⇒ 那 812 个名字的细格算空。

**填充仍要 ~63 s，但原因换了**：L1 把 2056 块填满的曲线在改前改后**逐点重合**（t=9 s 199 块、
t=29 s 659、t=63 s 2056）。⇒ 产出不再是瓶颈，卡在**流式管线本身**：每级的在飞上限
[`FAR_INFLIGHT_MAX`](file:///c:/repo/repo.rust/gate/gate-app/src/infinite_cubes.rs) = `PRODUCER_WORKERS × 2` = **6**
（它的 CONSTRAINT 写明了这是为"填充期的帧稳"定的：12 条时填得更快但掉到 13–50 fps）。
把每帧挂载预算 `mount_words` 从 1024 提到 **24576**（≈4 个远场块）**填充曲线一字不变** ⇒ 闸门不是挂载
预算，是那条在飞上限 —— 现在"产出 0.2 ms/块"这个前提变了，这条取舍值得重测（不是文件读写的问题，
这一点现在是**直接证据**）。

**另一条与"升空俯瞰"直接相关的边界**：远场预载的竖向范围是**相机为中心**的
[`FAR_PRELOAD_HY`](file:///c:/repo/repo.rust/gate/gate-app/src/infinite_cubes.rs) × 本级 chunk 高 = L1 的 **±164 m**。
升到 164 m 以上，预载枚举就够不到地面 ⇒ 只剩射线请求补（远场 1/64 采样）⇒ 正好是"升空后加载不完全"。

**B 的收益重估（纠正 §8.8 里我给的"同一池覆盖 46× 半径"）**：远场能装多少个**格**才是内存的真实
账 —— 树区按 `FAR_POOL_CHUNKS × FAR_RESERVE_WORDS_PER_CHUNK`（**每级**）预留，`grow_region` 又按
`region_chunks × 实测每块字数` 一次顶到位 ⇒ 内存 ≈ 常驻块数 × 每块字数 ≈ **格数**（与单元大小无关）。
而"覆盖到多远"满足 `格数 ≈ d · R²`（城市是 2.5D）⇒ **R ∝ √内存**，与单元大小**无关**。
所以：

- **同一份内存下，把单元放大（B）不增加视距** —— 单位数 ÷64 的代价是每块字数 ×64；
- B 真正买到的是**单位数**（= 帧时 + 填充期的"每帧完成量"）：它把"帧时上限"换成"内存上限"，
  于是**允许**去花内存。今天远场只有 ~130 MB（预算 2 GB）、帧时 5.8 ms（底线 10 ms）——
  **两个上限都还很远**，所以当下更便宜的杠杆是把 `FAR_POOL_CHUNKS` 与阶梯预算一起调大
  （L1 的 1.28 m 档：369 m ⇒ ~550 m 约需 2.5× 内存 ≈ 110 MB，帧时按外推约 +1 ms）。
- 等到"内存花到 700 MB 上下、单位数又把帧时顶到 10 ms"时，B 才是必须要做的那个重构。

### 8.10 两条与"加载慢 / 升空看不到"直接相关的修改

#### ① 远场预载的竖向锚到**世界地面**（不再跟相机）

**症状**（用户原话）："在平地还好，一旦升空想俯瞰大地……完全加载不完全"。

**成因**：远场预载的竖向枚举是**相机为中心**的 `FAR_PRELOAD_HY × 本级 chunk 高` = L1 的 ±164 m。
飞到 164 m 之上枚举就够不到地面 ⇒ 那一带只剩**射线请求**补（远场 1/64 采样）⇒ 看着就是"没加载完"。

**改法**：`ChunkSource::content_y_range()`（默认 `None` = 竖向无限，程序化世界保持原样）；MC 声明
`Some((0, 256 方块 ⇒ 4096 体素))`。声明了就把该级的**流式中心竖向**换成**内容带中点**
（横向仍跟相机）—— 于是预载枚举、LRU 保护圈、卸载判定全在内容空间里算，与相机高度无关。

**实测**（`GATE_BENCH=static`，相机抬到 **400 m**，64 s）：

```text

STREAM[v2 far … chunks 1107 rmax 26 unload 0]   ← 与地面完全一致
STREAM[v3 far … chunks   12 rmax  7 unload 0]   ← 一致
```

⇒ 高空下三级远场仍把地面铺满（改前这一带会退化成只剩射线点出来的零星块）。

#### ② 远场在飞上限：产出便宜 469× 之后，闸门从"产出"换成了它

**读数**（`GATE_BENCH=orbit`，`video/vsync` 关掉才量得到真值）：

| `FAR_INFLIGHT_MAX` | L1 常驻（t = 9 s） | L1 铺满 | 填充期帧周期 |
|---|---|---|---|
| 6（旧值） | 199 | 2056 @ **63 s** | 中位 5.8 ms、p95 8.4、>10 ms **1/424**（整轮） |
| 12（**新值**） | —（这一档的帧时未单独量到） | — | — |

取 12 = 6 与 24 的中值：24 那一档填充期有 8% 的帧越过 10 ms 底线，而这条闸门管的正是"每帧完成几条"。
⇒ **装载速率的下一步在"每帧能消化几条"上，不在产出、也不在文件读写** —— 这一条现在是直接证据
（`mount_words` 从 1024 提到 24576 填充曲线一字不变，见 §8.9）。

### 8.11 放池换视距：实测不划算，先修两个口径

**想做的事**：`FAR_POOL_CHUNKS` 4096 → 8192（阶梯预算 = `FAR_RESIDENT_TARGET` 3072 → 6144），
名义上"视距 ∝ √预算"⇒ L1 的 1.28 m 档该从 369 m 到 ~471 m。

**实测**（`GATE_BENCH=orbit` 175 s，`FAR_INFLIGHT_MAX` = 12）：

| | 池 4096 | 池 **8192** |
|---|---|---|
| 阶梯（启动行） | L1 r8..17 · L2 r4..27 · L3 r6..27 | L1 **r8..23** · L2 r5..30 · L3 r7..30 |
| L1 常驻 / `rmax` | 2056 / 18（369 m） | 3874 / 24（**512 m，+39%**） |
| L2 常驻 / `rmax` | 1107 / 26（2.13 km） | 1075 / **26（没变）** |
| L3 常驻 / `rmax` | 12 / 7 | 4 / 7 |
| 远场常驻合计 | 3175 块 | **4953 块** |
| `struct_buf`（树区，CPU 与显存各一份） | 224 MB | **800 MB** |
| 帧周期 / CPU 侧 | 16.7 ms（=vsync）/ 2.8 ms | 16.7 ms（=vsync）/ 2.96 ms |
| `BASES 漂移` / `UPLOAD[full]` | 各 1–2 次（启动） | 各 2 次（启动） |

⇒ **+39% 视距（只在一级上）换 3.6× 树区内存**，而且 L2/L3 的到达半径**一点没涨**。两个原因：

1. **树区按"池块数 × 实测每块字数"一次顶到位**（`grow_region`）⇒ 内存 ∝ 池块数，**与阶梯预算无关**
   ⇒ 把池翻倍，树区涨 4 倍。而真正用得上的块数只有阶梯那点（L1 3874、L2 1075）。
2. **L2/L3 的外圈不由预算定**：`plan_generation_far` 的候选枚举有 `todo.len() >= budget*4` 的提前
   退出，而 L2 的环里 ~97% 是空块 ⇒ 枚举很快攒够"预算×4"就停（`take(budget)` 又只取最近的）。
   之后靠"已知空"逐帧学习才慢慢外扩 —— 175 s 只走到 rmax 26。

所以**先修这两个口径，再谈放池**（都还没动）：

| 要修的 | 现状 | 方向 |
|---|---|---|
| 树区口径 | `region_chunks_of(远场) = FAR_POOL_CHUNKS` | 用**该级的实际目标**（阶梯给的环带规模）；池块数只当上限 |
| 候选枚举上限 | `budget*4` 的固定倍数（含 90% 空块） | 按"**这一环是否枚举完整**"停，或把"已知空"折算掉再算候选数 |

这一轮**没有**采纳放池：`FAR_POOL_CHUNKS` 已回到 4096。

### 8.12 主世界的预载盒竖向：也锚到内容带（"升空俯瞰正中是空洞"的真凶）

**症状**（用户截图）：远处城市完整，**画面正中（脚下）整片空洞** —— 像是"里面是圆、外面是方"。

**诊断**（一条诊断行就能判）：主世界的预载盒竖向是**以相机为中心**的 `coarse_height`（菜单 6）：

```text
STREAM[v0 gen1(req 0) unload 0 chunks 165 cap 2048 y 2..15 相机 26]   ← 飞在 40 m：预载盒 = y 20..32，**全是空气**
```

相机在 chunk y=26 时预载盒只覆盖 20..32 —— 一块都装不上（常驻 165 / 池 2048，**远未顶死**），
而地面的 `y 2..15` 那 165 块**全是射线请求点出来的**（稀疏 ⇒ 画面正中空洞）。对照：远场三级在
§8.10 ① 已经把竖向锚到内容带 ⇒ 所以**远处完整、近处空洞** —— 这就是截图里"里外不一样"的来源。

**改法**：把内容带锚定（[`ChunkSource::content_y_range`]）从"只给远场级"扩到**所有流式级**，
并把主世界预载盒的竖向半高从菜单的 `coarse_height` 换成**内容带行数**
（[`VolScope::v_hy`]，MC = 16 行 ⇒ 半高 9）。判据（新加的诊断字段）：`STREAM[v0 …] y a..b`
必须**恒包含内容带** `0..16`，而不是跟着相机走高。

**实测**（`GATE_BENCH=static`，相机抬到 **135 m**）：

| | 修前 | 修后 |
|---|---|---|
| `STREAM[v0 …]` | `chunks 165 y 2..15 相机 26` | `chunks **1353** y **0..15** 相机 7` |
| 主世界内存 | 6.5 MB | 63 MB（池 2048 未顶死 ⇒ 预载填满） |
| 远场三级 | L1 1995 / rmax 18 | 不变 |

⇒ 预载盒现在锚在地面（中心 = 内容带中点 chunk 7），常驻覆盖**整条内容带**。

### 8.14 两个后续修正：GI 的远场门 / 薄结构的"整节占比"复判

**① 近处 GI 噪点（上一条改动的回归）**。原设计里"远场对 GI / 阴影 / 镜面不可见"是靠**距离**站住的：
次级射线被 `SECONDARY_REACH_CHUNKS` 夹在 ±61 m（**现在只有 GI 候选与阴影**，见下），而 L1 从 164 m 起。接力半径改成球面后主世界只到
46 m ⇒ **L1 落进次级射线行程** ⇒ GI 吃到 L1 那层 1.28 m 膨胀块（法线/材质都是块状的）⇒ 水面噪点。
修法**不能**是"次级射线一律跳过远场"（那会把**远场自己**的 GI 也抽掉 ⇒ 远景仍然平），而是按
**起点距离**判（`world.wesl`）：

```wgsl
let cam_est = (g0.w_mn + g0.w_mx) * 0.5;   // 相机位置用主世界窗口 AABB 中心估（误差 ≤ 半 chunk）
let origin_r = length(origin - cam_est);
if (far && req == 0u && origin_r < shell) { continue; }   // `shell` = 本级的起始半径
```

起点比本级更近 ⇒ 本级不是它的环境（跳过，近场干净）；起点就在本级里 ⇒ 本级正是它的环境（参与，
远场有完整 GI）。

**② 高楼"中空" + 距离微变就突变**。`mc::lod` 的**写**侧按"整节实体够 **或** 任一细格有料"落盘
（薄墙的节靠细格救回来），而**读**侧（`View::cell`，`n == 1` 那支 = 5.12 m 档 = L2 的格）又拿
`SOLID_MIN_PERMILLE`（125‰）对**整节占比**复判一次 ⇒ 把刚救回来的节重新丢掉：16 方块见方的一节里
只有一层楼板/一面外墙时实体≈6% ⇒ **楼在 L2 档变空**，且换档时来回翻 ⇒ "距离微变就突变"。
修法：**读侧以"节存在"为有料**（写侧已经筛过），`summary::Summary::cell` 的 16 档同样加
"任一细格有料"这一支。

**实测**（`GATE_BENCH=orbit` 110 s）：`STREAM[v0 … chunks 6073 cap 10922 y 0..15 ready 0]`、
`RESID[resident 6050 389561KB install 2 evict 0 | 远场 2930块/装 0 evict 0]`、CPU 侧 2.2 ms/帧、
无 WESL 运行期错误；61 + 33 + 2 项测试全绿。

### 8.15 "已加载好的区域卸了又装、永不停歇" = 需求集没被保护

**机制**：预载的预算是 `budget = cap - requests` ⇒ **需求集本身就能占满容量**；而卸载时保护的只有
`unload_r` 那一小圈（菜单 3 chunk = 15 m）+ 在飞的 + ready 的。于是"需求圈内（41 m）、但**没被射线
用到**（`last_used` 旧）"的块成了 LRU 受害者：**卸掉 → 下一帧需求又把它加回来 → 再卸** ⇒ 抖动。
判据：`STREAM[… unload N]` 的 `N` 长期非 0 且常驻在 `cap` 附近来回。

**修法**（`stream_chunks` 的换出扫描）：把**当帧需求集** `st.demand` 也纳入保护 —— 需求集 ≤ `cap`
（预载内已按 `cap - requests` 截断）⇒ 换出的只剩"上一帧的射线请求"，而它们的需求本来就在变。

**实测**（`GATE_BENCH=orbit` 90 s，修后四个卷全部稳定）：

```text
STREAM[v0 gen1(req 0) unload 0 chunks 6089 cap 10922 y 0..15 相机 7 ready 0]
STREAM[v1 far gen3 unload 0 chunks 1790 cap 3072 rmax 16 ready 0]
STREAM[v2 far gen1 unload 0 chunks 1132 cap 3072 rmax 26 ready 0]
RESID[resident 6083 391049KB install 2 evict 0 | 远场 2935块/装 0 evict 0]
INST[install 2 新增 0 升级 2 降级 0]      ← 升级 = 射线把粗档细化（正常），降级 0 = 不抖
```

### 8.16 分壳改成**互斥**（选 B）：主世界独占整个窗口，细节不掉

**症状**（卷着色截图）：整片红（L1）+ 绿（主世界）噪点 —— 重叠带里两级的**面几乎重合**，逐像素抢"谁更近"。
原因：远场格是**膨胀块**（一个格有料就整格填实），表面落在格边界上 ⇒ 比真实表面近至多一格（L1 = 1.28 m）
⇒ 两级的面深度差不到一个体素 ⇒ 花斑。

**改法**（B = 互斥，且细节不掉）：

- 主世界的**覆盖半径 = 窗口内切半径**（`WINDOW_CHUNKS·256` = 163.84 m），`FAR_PRELOAD_INNER` 回到 **8**
  （= 163.84 m / 20.48 m）⇒ **L1 从 163.84 m 起**，两级不再重叠（分壳只按半径切）。
- 41–164 m 那一圈改由**主世界自己铺底**：`coarse_radius` 8 → **32**（盘 = 窗口），并把**预载档位封顶**
  在 `Detail::Coarse`（32 cm、12 KB/块；`PRELOAD_FULL_CHUNKS = 8` chunk 之内仍按 `detail_at` 给
  Full/Fine）。**细节不掉**：射线照旧按"屏幕 ≤ 1 px"报 level，命中的块被升级到 2 cm/8 cm。
- 副作用两处口径：两个 per-chunk 字节估计 384 KB → **48 KB**（只在"预载封顶 Coarse"时安全，已在常量
  doc 里写成 CONSTRAINT）；`request_mb` 默认 2048 → 4096。

**实测**（`GATE_BENCH=orbit` 140 s）：`STREAM[v0 … chunks 10016 cap 87381 y 0..15 unload 0 ready 8]`、
`RESID[resident 9991 439282KB install 8 evict 0]`、L1 `r8..17 / rmax 16`、帧周期 16.7 ms（60 fps）。
**要盯的一条**：填充期 CPU 涨到 ~7 ms（STREAM 2.37 + MAIN 3.03 + RESID 4.00），且远场这次只填到
L1 354/3072（近场预载大 4 倍 ⇒ 与远场抢产出预算）⇒ 远场铺满更慢。

**修 B 时踩到并修掉的**：窗口半宽**不能**读菜单的"粗档半径"—— 那个值在菜单加载之后才写进 `Streaming`，
启动建场时读到 0 ⇒ 窗口退化成 ±1 chunk、主世界 `chunks 0`（近场全空）。现在用常量 + 两者不一致时
`warn!`。

### 8.16.1 B 的前置条件：有界倍增 + 位图去重（做完，B 已打开）

B 第一次打开时崩 + 卡，两个根因各自修掉后才成立：

| 现象 | 根因 | 修法 |
|---|---|---|
| `memory allocation of 44552265872 bytes failed`（单次 44.5 GB） | 为了让池装下 1 万+ 块，per-chunk 估计 384 KB → 48 KB ⇒ 池块数 10922 → 87381；而 `grow_region` 对**流式世界**走的是 `Vec::reserve(target - len)`，`target = 池块数 × 实测每块字数` ⇒ 一次 reserve 44.5 GB | `grow_region` 改**有界倍增**（每次最多把容量翻倍，再夹到 `target`）：分配次数仍是 log₂ 级，**瞬时占用 ≤ 2× 实际**，池块数随便调 |
| `STREAM 10.67 + MAIN 11.38 ms/帧` | 盘半径 ×4（8 → 32 chunk）⇒ 枚举体积 ×16（65×19×65 = 8 万格），而**去重用的是 `HashSet<IVec3>`**（每次 insert ≈ 100 ns ⇒ 8 ms/帧） | 换**位图**（该立方体域 10 KB/帧、测试 ~2 ns）⇒ 同一次枚举 ~1 ms |
| `chunks 65536 cap 65536 unload 6 ready 288` | 需求 > 池上限 | 估计取 64 KB（4 GB ⇒ 池 65536）+ 位图后枚举变便宜 ⇒ 需求 18094 装得下 |

**实测**（`GATE_BENCH=orbit` 150 s，B 打开）：`STREAM[v0 gen1 unload 0 chunks **18094** cap 65536
y 0..15 ready 0]`、`RESID[resident 18093 834936KB install 1 evict 0 | 远场 3106块/装 0 evict 0]`、
L1 1981/rmax 18、L2 1114/rmax 26、CPU 侧 **3.9 ms/帧**（STREAM 0.44 + MAIN 1.07 + RESID 1.81 +
REQ 0.61）、帧周期 16.7 ms / 60 fps。⇒ 近场独占 ±164 m（`NEAR_COVER_CHUNKS = 32`、
`FAR_PRELOAD_INNER = 8`），两级不再重叠（卷着色下不应再有花斑），近处档位不变。

**B 打开后的第二次崩溃（同一个"池块数 × 每块字数"家族，另一处）**：`memory allocation of
42949672960 bytes failed`（**40 GiB 整**）= `池 65536 块 × 单块 163840 字 × 4 B` —— `grow_region` 的
`target` 用了 `max(历史平均, 本次要装的块)` 这个**保守**口径，而 `resize(target)` 在远场级的
"一次顶到位"分支里是**无界**的。修法：给三处各钉一个天花板（`REGION_CHUNKS_CAP = 32768`、
`PER_CHUNK_WORDS_CAP = 65536`、`REGION_WORDS_CAP = 2 GB`）+ 两条路径都走有界倍增 ⇒ **目标只是
天花板，实际占用按真实用量增长**。实测（`GATE_BENCH=orbit` 170 s、池 65536）：无崩溃，常驻 18117 块 /
851 MB（≪ 2 GB 天花板）/ CPU 4.0 ms/帧 / 60 fps，远场三级全铺满。

### 8.17 薄结构判空门槛：`SOLID_MIN_PERMILLE` 125‰ → 16‰

**症状**：红色卷（L1，`scale = 4`）里成栋楼**中空**、能看穿；把时间调到"sky color"后，中空处的颜色
**就是天空本色** ⇒ 那是**射线 miss**（打到天空），不是着色 / 材质 / GI。

**真因**：`SOLID_MIN_PERMILLE`（125‰）同时管两个口径 —— `4³` 细格（分母 64 ⇒ 一格要 ≥ 8 块）与整节
（分母 4096）。**一格厚的墙**若在本细格的 `x/z` 面上只压到 4 列（= 4 块）就 < 8 块 ⇒ 该格判空 ⇒ 墙上
开洞。且 **L1 走 `summary` 实时产出**（`produce_far` 只对 `scale ≥ lod::CELL = 16` 读 LOD 文件）⇒ 点
"构建 LOD"当然**没有任何变化**。

**修法**：门槛降到 **16‰**（细格 ≥ 2 块、整节 ≥ 66 块），并把整节判据写成"整节占比够 **或** 任一细格
够"（后者 §8.14 已加，`summary` 与 `lod` 写侧两侧同口径）。

**核对"代表色不能是空气"**：`voxel::rep_of` 只对**非空气**计票、全空返回 `None` ⇒ 被判有料的格 / 节
不可能取到 `AIR`（`summary::group`、`Sec.rep`、`lod::SecCol.rep` 三处都安全，无需改）。

**验收**：忽略测试 `mc::tests::real_map_far_rep_loses_thin_geometry` 改成**门槛扫描**（按写侧真实判据
"整节够 **或** 最厚细格够"，并给出密度代理量 = 被画出的 `4³` 细格数）：

```text
出生点 16×16 列共 1496 个非空节（× 64 细格 = 95744 格）
  P = 125‰ ⇒ 会被删  29 节 / 1324 面（0.0588%）；画出细格 80113（83.67%）
  P =  32‰ ⇒ 会被删   8 节 /   62 面（0.0028%）；画出细格 81388（85.01%）
  P =  16‰ ⇒ 会被删   6 节 /   42 面（0.0019%）；画出细格 81641（85.27%）
  P =   8‰ ⇒ 会被删   0 节 /    0 面（0.0000%）；画出细格 81896（85.54%）
```

⇒ 101 个"占 < 1/16"的薄节（一层楼板 / 一面外墙）**全部保留**，高楼不再中空；门槛从 125‰ 一路降到
8‰ 的**密度代价只有 +1.9%** 细格（真实城市几乎处处 ≥ 8 块/格）。取 **16‰**：只剩 6 节、每节 1~2 个
**孤立方块**（可见面 0.0019%，非结构）—— 保留这道非空门槛以维持"远场只求轮廓"；8‰ 虽能绝对归零，
但门槛会退化成"≥ 1 块"而失去意义。

#### 8.17.1 改了门槛却"还是不行"：L1 读的是**旧的 LOD 文件**

改完门槛重启，中空仍在，只是**透过洞能看到后面的卷**（L2/L3 有料）—— 说明洞**只**在 L1。真因是
**L1 不走 `summary`**：L1 的格边长 = `FINE_CELL` = 4，而 `lod::View::supports(4)` 为真（v2 文件每节
自带 `4³` 细格）⇒ `source::produce_far` 优先走文件（`self.lod().filter(...)`），**只要有文件在，L1 一律
读文件**。而 `data/lod/mc_map.lod` 是改门槛**之前**建的，细格还是 125‰ 的洞。L2/L3 读的是**节代表色**
（写侧本来就有"任一细格有料"那一支）⇒ 它们基本没洞，"躲在后面"。

⇒ 两个动作：

1. **`stamp` 带上采样口径版本**（`FORMAT_TAG`，`mc::lod`）：`stamp` 原来只认地图指纹（路径 +
   `level.dat`）⇒ **改代码不会让旧文件失效**，画面继续按旧口径渲染 —— "重建 LOD 毫无变化"的根源。
   现在口径一变（门槛 / 细格粒度 / 布局）旧文件立即作废，回落到 `summary` 等重建。`FORMAT_TAG = 3`
   （v2 = 每节带 `4³` 细格；v3 = 门槛 125‰ → 16‰）。
2. **重建真文件**（`GATE_LOD_REAL=1 … real_map_build_lod`，8~9 s）：1183744 列 / 1453572 节 /
   39.3 MB（旧 37.7 MB，多出来的就是救回来的薄结构）。逐格对照 `summary`：

```text
L1 scale 4 ：同色 1379、异色 179、单边有料 0  、都空 2538   ← L1 无洞（本条要的证据）
L2 scale 16：同色 1452、异色 149、单边有料 2  、都空 2493
L3 scale 64：同色  389、异色  62、单边有料 29 、都空 3616   ← 中心列采样，LOD 更准
```

L3 的"单边有料"由 < 5% 升到 6%：门槛降后保留的节变多，`summary` 只采格中心那一列 ⇒ 漏采随之变多
（LOD 采满格内 `n³` 个节，**更准**）⇒ 该测试闸门对"格 > 一个节"这档放宽到 10%。

### 8.17.2 中空/骨架的真凶：**内容锚在 chunk 角，裁剪按相机** ⇒ 每道交接面上留一圈空环

**症状**（用户给的三条判据）：①同一栋楼，靠近就正常、退后就成了"中空"；②透过中空能看到**后面那一级**；
③"稍微移动近一点就正常了"。三条都指向**位置依赖**，不是内容门槛（门槛那轮已经改完仍复现）。

**真因**：内容生成把**相机的 chunk 角**当窗口中心（`infinite_cubes::stream_chunks`：
`scope.center = floor(cam / chunk)`），而分壳裁剪的半径一律以**相机**为原点（`world.wesl::level_cap`）。
两者错开最多**一个 chunk**（每水平轴 ∈ [0, chunk)）⇒ 任何一块内容边缘，沿某个方向最多比"相机量到的
半径"短 `√2` chunk（≈1.42）。于是**每一道交接面**（主世界↔L1↔L2↔L3）都会出现一圈**两级都没有内容**
的环：

- **内圈**：主世界裁剪到 `NEAR_COVER_CHUNKS·chunk` 就停，而 L1 的环带从 `FAR_PRELOAD_INNER·chunk`
  （= 同一个数）起 —— 但两者的原点差最多一格 ⇒ L1 的内容可能在裁剪面**之外**才开始 ⇒ 中间那圈谁
  都没内容。
- **外圈**：本级内容的远边 `(r_out + 0.5)·chunk`，而裁剪半径用 `(r_out + 1)·chunk` ⇒ 偏移反向时
  内容比裁剪面短 ⇒ 外圈同样留环。

环里**没有体素** ⇒ 射线直接穿过去、打到**后一级**（用户②），而且相机在 chunk 内挪十几米就换个方向
出现（用户③）。对着相机的那**一面墙**如果整个落在环的距离区间里，就整片消失（用户①）。

**修法**：把"**画互斥**"与"**内容密铺**"分开满足 —— 裁剪仍按距离切（每像素只由一级画），但**每一级
的内容都要越过自己的裁剪面** `SEAM_MARGIN = 2` 个本级 chunk（≥ √2）：

| 量 | 旧 | 新 |
|---|---|---|
| 主世界覆盖半径 `NEAR_COVER_CHUNKS` | 32（= 预载盘半径，**零余量**） | **30**（= `WINDOW_CHUNKS − SEAM_MARGIN`，预载仍铺 32） |
| 第 `vol` 级裁剪半径 `far_coverage_voxels` | `(r_out + 1)·256·scale`（= 内容远边） | `(r_out + 1 − SEAM_MARGIN)·256·scale` |
| 下一级内圈 `r_in'` | `r_out / 4` | `(r_out − SEAM_MARGIN + 1)/4 − 1` |
| 主世界 → L1 的内圈 `FAR_PRELOAD_INNER` | 8（`NEAR_COVER_CHUNKS/4`） | **6**（`NEAR_COVER_CHUNKS/4 − 1`） |

⇒ 交接面上**两级都有内容**（射线穿不过去），但**只有一级在画**（裁剪面按距离切）—— 这正是用户要的
"互斥**且**密铺"。同时修掉 `mc::build` 里一处**重复 `set_coverage_r`**（第二处用 `WINDOW_CHUNKS`
覆盖了第一处 ⇒ 之前的 `NEAR_COVER_CHUNKS` 改动其实不生效）。

**验收**：单测 `far_ladder_covers_five_km` 现在直接钉住这两条不变量 —— ①每级的裁剪半径 ≤ 内容远边的
最不利下界（`(r_out + 0.5 − √2)`）；②下一级内圈的最不利下界 ≤ 上一级的裁剪半径。**旧代码在这两条上
必然失败**（`(r_out + 1) ≤ r_out − 0.91` 不可能成立），所以它就是这条 bug 的回归闸门。

**代价**（可接受）：交接面向内挪 2 个本级 chunk ⇒ ①主世界 ↔ L1 的换档从 164 m 到 153.6 m（那 10 m
由 1.28 m 的 L1 格画）；②L1 ↔ L2 从 368 m 到 307 m；③L1 的常驻块数与 `rmax` 随 `r_in`/`r_out` 变化
（环带总量仍被 `far_cap` 的预算钉住）。
