# Devlog #13 - OPTIMIZING my physics engine

- 视频: https://youtu.be/b_d-0EyOuVg （9:30，2023）
- 类别: 物理

## 一句话
物理引擎性能三件套：对象消亡（融合回地形）、对象休眠（邻域不变即跳过）、CPU 多线程（线程池 + 事件系统并行），23ms→9ms。

## 内容要点
- **Despawn + 融合回地形**（评论区网友的点子）：砍树/挖洞的碎屑体素久置后不做「消失」而是**仿射变换后重新光栅化融合进主体素网格**成为地形一部分；且等玩家**背过身去**才执行——不观察就不突兀。树不用再吃物理开销。
- **对象休眠**：跟踪每个对象上次被物理改动的时间；处理它时检查「上 tick 它自己没变 + 邻近对象最近几个 tick 没变」→ 物理结果必然相同 → 整个跳过。效果：砍 10-20 棵树后碰撞检测从 14-15ms 回落到稳定（单棵树碰撞 1-2ms，tick 预算 25ms）。
- **CPU 多线程**：线程池按对象分配到核；10 棵树的碰撞检测单核 23ms → 4 线程 9ms（>50% 提升）。
- **任务级并行**：事件系统 geese 多线程化——互不依赖的 system 并发处理事件，各 system 视角内仍保持顺序性；加并行=加 system。作者向 Bevy 用户发问：事件驱动 vs ECS？（他自评事件驱动处理一次性事件更顺手，ECS 只是它的一个 system）

## 对 gate 的启示
- **休眠判据 = gate 脏组件队列的反向表述**：「自己 + 邻域近几 tick 无变化 → 跳过」可直接作为 gate 事件驱动模拟的休眠层（脏队列只收「真的脏」的，休眠层负责连检查都省掉）。
- tick 预算 25ms/帧的预算意识与 gate per-tick work budget 一致；「砍树越多越卡 → 休眠后线性回落」是预算压力测试的现成场景设计。
- 「玩家背身时执行重操作」的 UX 技巧可借鉴到 gate 的 refinement 合并回/ LOD 重构（避开玩家注视）。
- 他的 geese 事件系统多线程化结论对 gate 的 CPU 事件驱动模拟有参考价值：系统间依赖图决定并行度。
